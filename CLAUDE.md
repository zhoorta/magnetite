# Magnetite

Theme-first music player for the web: persistent player, live audio visualizers, themes as shareable JSON bundles. Personal/fun project, same maker as Ferrite.

- Read `PLAN.md` first: scope, positioning, build order and status. Keep its checkboxes updated as work lands; put detail in `docs/`, not in the plan.
- Stack: Laravel 13, Livewire 4, Alpine (bundled with Livewire), Tailwind 4, Vite, Pest 5 (needs PHPUnit 13), getID3. Flux UI not installed yet.
- Livewire is imported through Vite (`livewire.esm` + `@livewireScriptConfig` in the layout) so `Alpine.store('player')` can be registered in `resources/js/magnetite/boot.js`.
- The player lives in an `@persist('player')` block in `resources/views/components/layouts/app.blade.php`; the `<audio>` element and the Web Audio graph must never be recreated on navigation.
- `wire:navigate` wipes inline CSS variables on `<html>`; the theme is re-applied on `livewire:navigated`. Keep that in mind for anything else set on `<html>`.
- `/` is the start page; `/library`, `/shared`, `/stream`, `/cover` and `/upload` need a signed-in user (username and password, `php artisan magnetite:user`). The sign-in page uses the `bare` layout (no nav, no player).
- Multi-user (`docs/multi-user.md`): every album and track has a `user_id`; files live in `MAGNETITE_MUSIC_PATH/users/{username}` and `tracks.path` is relative to that folder. Who may use a track is decided only by `Track::visibleTo()` / `TrackPolicy` (own, or in `shared_items`), answered with 404; keep the scope and the policies in step. Files are reached only through `TrackLibrary::resolve($path, $owner)`. The old root library is moved with `magnetite:claim {username}`.
- Scans run on the queue, one user at a time (`App\Jobs\ScanLibrary::request($user)`, status per user in `App\Support\ScanStatus`); a queue worker must be running (`composer dev` has one). `magnetite:scan [username]` without `--queue` scans inline.
- Deploy image: `Dockerfile`, `compose.yaml`, `docker/` (FrankenPHP, ffmpeg, Node; web and queue worker from one image, SQLite in a volume), see `docs/docker.md`. Rebuild it to check changes to extensions or the entrypoint.
- Streaming is the security surface: files are served only through `/stream/{track}` with a type allowlist, `nosniff` and `Content-Disposition: inline`; never expose paths.
- Run `vendor/bin/pest` and `vendor/bin/pint --test` before committing. First commit made 2026-10-08, no remote yet; no Claude trailer in commits (same as Ferrite).
- The library is read from `MAGNETITE_MUSIC_PATH`. The only writer is `App\Services\LibraryUploader` (zip upload into the uploader's own folder, see `docs/auth-and-upload.md`): audio and cover images only, nothing overwritten, unsafe paths abort the archive; keep it that strict. `php artisan magnetite:scan` fills `albums`/`tracks` via `App\Services\LibraryScanner`; covers go to `storage/app/private/covers/{sha1}.jpg`. Tests use committed fixtures in `tests/Fixtures/music` and `Storage::fake('local')`.
- Playlists are private (`PlaylistPolicy`, 404 for others) and hold references; what a person may play from one is decided by `visibleTo` (`Playlist::tracksFor($user)` marks `open`, `playableBy()` filters), never by the raw relation; a shared playlist must not carry stream urls of tracks the viewer cannot play. Keyboard shortcuts live in `onKey()` of the player store in `boot.js`; pages must pass the player a copy of their track array (`setQueue([...tracks], i)`) when they edit it.
- Alpine runs `init()` and `destroy()` methods of an `x-data` component automatically (on creation and on removal, so on every `wire:navigate`); never name an action method `destroy`.
- Rebuild assets (`npm run build`) after editing Blade views that add Tailwind classes, or the served CSS is stale.
- ALAC is served as FLAC through `App\Services\TranscodeCache` (ffmpeg, `MAGNETITE_FFMPEG` or PATH). The source is only ever an already-validated absolute path passed as a process argument array, never through a shell.
- Visualizer contract (`resources/js/magnetite/visualizers/`): each module has `id`, `label`, `needs` (which of `freq`, `wave`, `levels`, `bands`, `spectrum` it reads; the engine computes only those; `lufs` and `stereo` come from the meter worklet and are always current), default `params` and `draw(g, sample, {w, h, colors, params, dt})` on the single 2D canvas. Several can be shown at once (`layout.js`, up to 4 panels): each is drawn in its own clipped cell, so use only the `w`/`h` you are given, never the canvas size; which meters show is the user's own list (`users.meters`, default `['vu-wide']`, saved by `PUT /settings/meters`, handed to the page as `window.magnetite` in the head partial); a theme can only give a look (`visualizers: [{id, params}]`) to meters the user has chosen. Samples carry `freq`, `wave` and per-channel `levels`; before the first play they carry silence so visualizers draw an idle state.
- Sample-accurate meters (LUFS, true peak, correlation, goniometer) live in `resources/js/magnetite/worklet/meter-processor.js`, an AudioWorklet that is also imported by the Node tests (`npm run test:js`; keep it self-contained, no imports). The engine fetches the worklet file at construction and loads it from a Blob URL: `php artisan serve` is single-threaded, so a worklet request made during playback queues behind the audio stream and never loads.
- File truth (`docs/file-truth.md`): `php artisan magnetite:analyze` runs `bin/measure.mjs` (Node, ffmpeg and ffprobe needed) per track and stores `tracks.analysis` (JSON), `dr` and `pcm_sha1`. The thresholds that decide what is a problem live in `App\Support\FileTruth`, not in the stored data. `TrackAnalyzer::VERSION` must be raised when a measurement changes. Pest tests that need the tools skip without them; `npm run test:js` runs the Node tests (also needed before committing changes under `resources/js/magnetite/worklet` or `analysis`).
