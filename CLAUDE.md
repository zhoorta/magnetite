# Magnetite

Theme-first music player for the web: persistent player, live audio visualizers, themes as shareable JSON bundles. Personal/fun project, same maker as Ferrite.

- Read `PLAN.md` first: scope, positioning, build order and status. Keep its checkboxes updated as work lands; put detail in `docs/` (index: `docs/README.md`), not in the plan; the old dated log is `docs/history.md`.
- Stack: Laravel 13, Livewire 4, Alpine (bundled with Livewire), Tailwind 4, Vite, Pest 5 (needs PHPUnit 13), getID3. Flux UI not installed yet.
- Livewire is imported through Vite (`livewire.esm` + `@livewireScriptConfig` in the layout) so `Alpine.store('player')` can be registered in `resources/js/magnetite/boot.js`.
- The player lives in an `@persist('player')` block in `resources/views/components/layouts/app.blade.php`; the `<audio>` element and the Web Audio graph must never be recreated on navigation.
- `wire:navigate` wipes inline CSS variables on `<html>`; the theme is re-applied on `livewire:navigated`. Keep that in mind for anything else set on `<html>`.
- `/` is the start page; `/library`, `/shared`, `/stream`, `/cover` and `/upload` need a signed-in user (username and password, `php artisan magnetite:user`). The sign-in page uses the `bare` layout (no nav, no player).
- The library page is the dense, keyboard-first view (`docs/dense-library.md`, mockup `docs/mockups/dense-library.html`): `LibraryController` builds one data array (HTML page and `GET /library` as JSON), `resources/js/magnetite/dense/component.js` draws it; the row model (`rows.js`) and the key table (`keymap.js`) are pure and tested by Node. Its keys apply only while the library itself has focus (`e.target === $root`); the player's keys still work through `onKey()` (it skips events the library already took with `preventDefault`). `N`, `A`, `S` and `v` belong to the library; don't bind them in the player. The library redraws from `reload()` (JSON), never by swapping DOM. `users.ui` (`PUT /settings/ui`) keeps the per-user info level and meter tint, read through `Alpine.store('ui')` (`dense/ui.js`; key `I` is global, `n` and `p` are lowercase only); what the lists and the player bar say about a file comes from `dense/info.js`, so the thresholds stay in `FileTruth`. The player's meter keys are the terminal client's (`m M + - [ ]`, `c`, `t T`, `Tab` in full screen); the library ignores keys while the player is full screen; digits still seek. The library's command line is `dense/commands.js` (pure) plus `runCmd()` in the component: a new command is an entry in `COMMANDS` and a case there, and should also have a key or a button. The page data is a JSON script block (`#library-data`), not an attribute, and the long spectrum curve of a track is fetched on demand (`GET /library/tracks/{track}/spectrum`; the library data has `spectrum_points`). The left pane has three modes (`mode`: tree, search, truth) with a key table each in `keymap.js`; in the other two modes the tree's actions are off. `$root` and `$refs` are tied to the x-data and the element that run a handler (inside a menu `$root` is the menu): use `this.libraryRoot`, and after `$nextTick` use `afterUpdate()`. Search is `GET /search` (`SearchController`, `LibrarySearch`). The edit table saves through `PATCH /library/albums/{album}/details` (all or nothing). The tint (`dense/palette.js`, `Alpine.store('ui').shade()`) only changes the colours handed to the visualizers each frame.
- Themes: `themes.json` plus the ones a browser added (`magnetite.themes` in localStorage, merged in `boot.js`; the player store has `addTheme`/`replaceTheme`/`removeTheme`). Anything imported or edited goes through `themes.js` (`validateTheme`: hex colours, a radius, a safe font; tested by Node), because the values end up in CSS variables. The themes page is `themeStudio` (`themes-page.js`: preview, edit a copy, download/copy JSON, import), laid out like the Scenes page: the themes as a strip on top, the preview and the live meter on the left (sticky), the settings in groups (colours, type and shape, meter settings) on the right and the top bar has a palette dropdown (`components/themes-menu.blade.php`). Custom themes are per browser, not per account. Fonts: the studio offers the list `FONTS` in `themes.js`; the 16 bundled ones, in groups (sans, rounded and display, serif, mono, pixel and terminal; all but a few are Ferrite's too; all OFL, latin subset from the `@fontsource` dev dependencies; `FONT_GROUPS` feeds the pickers) are declared in `resources/css/fonts.css` and only downloaded when something on the page uses them; a new one needs a `@font-face` there and an entry in `FONTS` (a Node test checks both, and that the files exist). A theme file stores the font-family stack, so an imported theme that names a font we do not bundle falls back to the next family in its stack; the apps and the terminal client ignore the font. A theme may also carry `meterFont` (same check as `font`, left out = the meters follow `font`): `applyTheme` sets `--font-meter`, `readColors()` hands it to the meters as `colors.font`, `font-load.js` asks the browser to load its first family (a canvas does not start downloads), and the studio has a "Meters" font select. The meter settings a theme may carry are listed in `meter-schemas.js` (key, label, range, colour or number; a colour left unset follows the theme): `themes.js` clamps numbers and drops other keys for those meters, and the studio draws its controls and a live preview from the same list. A new param on a meter needs an entry there, or a theme cannot set it (a Node test checks every entry against the meter's own `params`).
- Upload: the `uploads` store (`uploads.js`, config in `window.magnetite.uploads`) does the XHR and polls the scan, so an upload goes on while you navigate; `components/upload-panel.blade.php` is the one panel, used by the page `/upload` and by the library's dialog (`U`, `:upload`, the toolbar icon). Zips dropped anywhere on the library page start uploading; when the scan the page asked for finishes it fires `magnetite:scanned` and the library reloads. The status line shows `$store.uploads.note`.
- Multi-user (`docs/multi-user.md`): every album and track has a `user_id`; files live in `MAGNETITE_MUSIC_PATH/users/{username}` and `tracks.path` is relative to that folder. Who may use a track is decided only by `Track::visibleTo()` / `TrackPolicy` (own, or in `shared_items`), answered with 404; keep the scope and the policies in step. Files are reached only through `TrackLibrary::resolve($path, $owner)`. The old root library is moved with `magnetite:claim {username}`.
- Scans run on the queue, one user at a time (`App\Jobs\ScanLibrary::request($user)`, status per user in `App\Support\ScanStatus`); a queue worker must be running (`composer dev` has one). `magnetite:scan [username]` without `--queue` scans inline.
- Deploy image: `Dockerfile`, `compose.yaml`, `docker/` (FrankenPHP, ffmpeg, Node; web and queue worker from one image, SQLite in a volume), see `docs/docker.md`. Rebuild it to check changes to extensions or the entrypoint.
- Live (since 2026-10-09): magnetite.stackcare.pt runs without Docker, see `docs/bare-metal.md`: nginx + PHP-FPM 8.5 (own pool and socket, other sites share the FPM), MySQL, systemd `magnetite-queue`, Linux user `magnetite`, code in `/var/www/magnetite/app` pulled from GitHub with a deploy key, libraries in `ferrite.stackcare.pt` (same host). Deploy = `git pull`, composer, `npm run build`, `migrate --force`, `optimize`, `queue:restart`, FPM reload. Next: a test from a US server to measure remote Ferrite latency.
- Streaming is the security surface: files are served only through `/stream/{track}` with a type allowlist, `nosniff` and `Content-Disposition: inline`; never expose paths.
- Run `vendor/bin/pest` and `vendor/bin/pint --test` before committing. First commit made 2026-10-08, no remote yet; no Claude trailer in commits (same as Ferrite).
- The library is read from `MAGNETITE_MUSIC_PATH`. The only writers are `App\Services\LibraryUploader` (adds) and `App\Services\LibraryRemover` (the owner's Delete button on albums and tracks: unlinks the file in a local folder, moves it to Ferrite's trash with a `trash` token; rows follow the files; cover images stay) (zip upload into the uploader's own folder, see `docs/auth-and-upload.md`): audio and cover images only, nothing overwritten, unsafe paths abort the archive; keep both that strict. `php artisan magnetite:scan` fills `albums`/`tracks` via `App\Services\LibraryScanner`; covers go to `storage/app/private/covers/{sha1}.jpg`. Tests use committed fixtures in `tests/Fixtures/music` and `Storage::fake('local')`.
- Playlists are private (`PlaylistPolicy`, 404 for others) and hold references; what a person may play from one is decided by `visibleTo` (`Playlist::tracksFor($user)` marks `open`, `playableBy()` filters), never by the raw relation; a shared playlist must not carry stream urls of tracks the viewer cannot play. Keyboard shortcuts live in `onKey()` of the player store in `boot.js`; pages must pass the player a copy of their track array (`setQueue([...tracks], i)`) when they edit it.
- The player's queue, current track and position are saved in `localStorage` per user (`savePlayback` / `restorePlayback` in `boot.js`) and restored paused after a reload; any new way of ending the session must call `forgetPlayback(true)`. A restored page must never start sound by itself. The start page calls `$store.player.preload(tracks)` for its demo music: it loads the first track paused, and does nothing when a track is already loaded or this person has a saved queue; demo tracks (`demo: true`) are never saved.
- Alpine runs `init()` and `destroy()` methods of an `x-data` component automatically (on creation and on removal, so on every `wire:navigate`); never name an action method `destroy`.
- Rebuild assets (`npm run build`) after editing Blade views that add Tailwind classes, or the served CSS is stale.
- ALAC is served as FLAC through `App\Services\TranscodeCache` (ffmpeg, `MAGNETITE_FFMPEG` or PATH). The source is only ever an already-validated absolute path passed as a process argument array, never through a shell.
- Visualizer contract (`resources/js/magnetite/visualizers/`): each module has `id`, `label`, `needs` (which of `freq`, `wave`, `levels`, `bands`, `spectrum` it reads; the engine computes only those; `lufs` and `stereo` come from the meter worklet and are always current), default `params` and `draw(g, sample, {w, h, colors, params, dt})` on the single 2D canvas. Several can be shown at once (`layout.js`, up to 4 panels): each is drawn in its own clipped cell, so use only the `w`/`h` you are given, never the canvas size; which meters show is the user's own list (`users.meters`, default `['vu-wide']`, saved by `PUT /settings/meters`, handed to the page as `window.magnetite` in the head partial); a theme can only give a look (`visualizers: [{id, params}]`) to meters the user has chosen. Samples carry `freq`, `wave` and per-channel `levels`; before the first play they carry silence so visualizers draw an idle state.
- Poster meters (`visualizers/poster-*.js`, helper `poster.js`, `docs/posters.md`): each draws in its own 600 x 800 space (`begin()` scales and centres it in the cell), prints the playing track from `track`, and has the common settings `text`, `theme` and its own colours in `meter-schemas.js`; the `needs` are as above. The test in `themes.test.mjs` reads each module's `params` block as text, so keep one `key: value,` per line, and no `params:` or `draw(` earlier in the file.
- Sample-accurate meters (LUFS, true peak, correlation, goniometer) live in `resources/js/magnetite/worklet/meter-processor.js`, an AudioWorklet that is also imported by the Node tests (`npm run test:js`; keep it self-contained, no imports). The engine fetches the worklet file at construction and loads it from a Blob URL: `php artisan serve` is single-threaded, so a worklet request made during playback queues behind the audio stream and never loads.
- File truth (`docs/file-truth.md`): `php artisan magnetite:analyze` runs `bin/measure.mjs` (Node, ffmpeg and ffprobe needed) per track and stores `tracks.analysis` (JSON), `dr` and `pcm_sha1`. The thresholds that decide what is a problem live in `App\Support\FileTruth`, not in the stored data. `TrackAnalyzer::VERSION` must be raised when a measurement changes. Pest tests that need the tools skip without them; `npm run test:js` runs the Node tests (also needed before committing changes under `resources/js/magnetite/worklet` or `analysis`).
