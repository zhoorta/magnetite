# Terminal client

Status (2026-11-09): started in `tui/` (Rust). Same `/api/v1` as the mobile apps; no server changes. Builds, the decoder is tested on the fixtures (`cargo test` in `tui/`); not yet tried against a running server or through the speakers.

## Why Rust and native audio
The point is real meters (spectrum, VU, correlation, later LUFS and true peak), which need the samples. An mpv backend would be less code but gives no access to them. So the client decodes itself: `symphonia` (FLAC, ALAC, MP3, AAC, Ogg, WAV) into `cpal`, with a tap of the last 4096 frames that the UI thread turns into meters (`rustfft`).

## Use
```
cd tui && cargo run --release -- login https://magnetite.stackcare.pt   # shows a code, approve it at /device
cargo run --release                                                      # the player
```
The token is kept in `~/.config/magnetite/tui.json` (mode 600). Keys: `j/k` move, `enter` open an album or play from a track, `space` pause, `n`/`p` next and previous (`p` and the system's previous restart the track when it is more than 3 s in), `,`/`.` seek ∓10 s, `tab` choose the active meter panel (its title is marked ▸), `m`/`M` next/previous meter for it (never one already shown), `+`/`-` add or remove a panel (0 to 4, 2 x 2; `-` removes the last one too and `m` or `+` brings one back), `c` meter colours from the cover on/off, `L` loudness matching (off, album, track), `/` search (below), `A` analyse the selected album or track (below), `i` file-truth table (below), `f` full screen (esc closes), `t`/`T` next/previous theme, `h` back, `?` help, `q` quit.

## Meters
Same contract as the web visualizers: each draws only into the cell it is given (`src/panels.rs`), and the ids are the web's. Drawn: `vu-wide` (the web's look: two long shallow windows, 4.2 : 1, a 28° scale arc with the pivot far below so the needle sweeps sideways, red zone from -6, ticks every 2 dB, labels, clip lamp; stacked or side by side by whichever is bigger, centred; the window is the theme's `surface`), `vu-leds` (level bars with peak hold), `third-octave` (31 ISO bands, 3 dB/octave tilt), `spectrogram` (half blocks, about 10 columns a second), `scope` (braille, rising-edge trigger, auto gain), `goniometer` (braille, mid/side), `loudness` (live M, S, I, LRA and true peak from the `ebur128` crate fed with every sample played, plus a minute of momentary history), `vu-needle` (the web's `dial.js`: two faces 1.55 : 1 side by side and centred, 96° scale of -30..+3 dBFS with the pivot near the bottom, red from -6, ticks every 2 dB, labels, "dB", L / R, clip lamp, needle with tail and hub, 0.3 s VU ballistics, braille), `magic-eye` (two tubes whose shadow wedge closes with the level, 78° open at silence, same ballistics as the web) and `spectrum` (24 log bars, terminal-only). All the web's meters are drawn now. Which meters show: this client's own list in `tui.json` (`tab`, `m`, `+`, `-`), else the account's list from `/me`, else spectrum and wide meters. Changing it here does not touch the account setting.

## Full screen
`f` is the web's full screen: the page background, the meters filling the terminal with no borders, laid out by aspect ratio like `layout.js` (a wide terminal puts two side by side, a tall one stacks them; 2 x 2 beats 3 + 1; the same rule is used in the small dock), then the title, artist (accent) and album, the progress line and a hint with the active meter. Playback keys, `tab`/`m`/`+`/`-` and `t` keep working; browsing keys are off. `esc` or `f` returns.

## Help
`?` opens a centred panel with the keys of the view you are in (library, file-truth table, search, full screen, A/B compare), grouped; `?` or `esc` closes it and every other key is ignored meanwhile. The table is in `src/help.rs`, so a new key goes there and in the key handler. In the search box `?` is text. The library footer is short now (`? all keys · …`), and `magnetite --help` points at `?`.

## Upload
`magnetite upload PATH…` sends music to the server without the web page. A path is a zip (sent as it is), a folder (zipped to the temp folder first, audio and cover images only, uncompressed, deleted afterwards) or audio files (sent as single files, which land loose in your folder). One request per path, with a percentage, then it waits for the scan (`/scan`, polled every 2 s, 30 minutes at most) and lists the albums that got tracks from this upload (`GET /albums?since=`, the server's clock from the upload's answer). The rules are the server's (`LibraryUploader`: audio and covers only, nothing overwritten, unsafe paths refuse the zip, quota).

Then, per new album, in a terminal: `i` MusicBrainz titles (each candidate with the per-track change `old → new` and its fit, then yes / next / skip; titles, date and label are applied), `c` look for a cover on the web, `e` edit artist, album and year, `enter` next album, `q` stop. Flags: `--identify` applies the best MusicBrainz candidate without asking when its fit is 80% or more and every track found a title (otherwise nothing is changed); `--cover` looks for a cover for every new album (an album that has one is left alone); `--artist X`, `--album X`, `--year N` set those fields on every new album; `--no-review` skips the menu (also skipped when the input is not a terminal). Needs a write token (the device sign-in gives one).

Files with no album tag are not albums after the scan, they stay loose tracks. For each folder of them from this upload the client asks for an album name (the folder's name is the default, `-` leaves them loose), artist and year, or takes `--album`, `--artist` and `--year` for every folder; without either (not a terminal, no flags) they are reported and left alone. The album is made by `POST /api/v1/albums` from `GET /api/v1/tracks/loose?since=` (see `docs/android.md`). Not done: chunked or resumable upload (one big zip over a slow link is one request), choosing between several covers (the server picks the first it finds), the review inside the full-screen player, MusicBrainz for a folder of untagged files (the web's `/identify` does that; here the names are yours).

## Analyze
`magnetite analyze` starts the server's file analysis (the same as `magnetite:analyze` and the web's "Analyse": DR, LUFS, true peak, clipping, lossy-source findings) and follows it: `--all` (everything without a current analysis), `--album ID`, `--track ID`, or a search text that leads to one album (several are listed, and chosen at a terminal; otherwise pass `--album`). It polls `GET /analysis` every 2 s (`running: 12 of 74 tracks · file`), then prints the album's tracks with marker (✗ problem, ! warn, · note), number, title, format, DR, LUFS, true peak and the finding labels, and a line with the counts and the mean DR; a track prints its findings with their explanations. `--no-wait` queues and returns, `--status` shows the run. The server only measures tracks that have no analysis of the current version, so asking again for an analysed album does nothing ("nothing to measure"). `upload --analyze` queues the analysis of every new album right after the scan, lets you review them while it runs, and prints the reports at the end. Needs `node`, `ffmpeg` and `ffprobe` and a queue worker on the server (the API says so when they are missing). `A` in the library view does the same from the player: on the album list it analyses the selected album, on the track list the selected track. The request and the following run on a background thread; the footer shows `analysing: running: 12 of 74 tracks · file`, then the result, and the open album is read again (its tracks show their numbers) and the file-truth table loads again at the next `i`. One analysis at a time from the player. The wait also ends when the album's own entry in the run says done, because the server's overall state can stay "queued" for a while after a job that was over in under a second (seen on a fresh local server: a miscounted waiting-jobs counter in `AnalysisStatus` that only wears off after an hour; not investigated yet). Not done: re-measuring files that already have an analysis, analysing from the file-truth table.

## Album order
The album list is sorted by the artist that is shown (`display_artist`), then year, then title, in the client too (`sort_albums`), so an album without an album-artist tag sits under its tracks' artist (Quicksilver Messenger Service among the Q's) instead of at the top; the server now sorts the same way (`Album::inLibraryOrder()`).

## Search
`/` opens the search (from the lists or the truth table). It uses the server's `/search`: albums and tracks whose title or artist contains the text, yours and what is shared with you (at most 25 albums and 50 tracks). While you type, every key is text, so `q`, `n` or `p` do not fire; a request goes out 250 ms after the last key and only for two letters or more (the server refuses fewer), and an answer to older text is dropped. `enter` or `down` moves into the results (`delete` clears the text, `esc` closes). In the results `j`/`k` and `PgUp`/`PgDn` move, `enter` plays a track (the tracks among the results become the queue, so `n` goes on to the next hit) or opens an album in the library view, `/` or `esc` goes back to typing, and the player keys (`space`, `n`, `p`, `,` `.`) keep working. Since 2026-11-11 the server matches word by word (`App\Services\LibrarySearch`, below), so `bowie heroes` finds *Heroes* by Bowie and a track is found by its album's name. The words you typed are shown bold and underlined in the results (title, artist and album, folded like the server does: case and accents), albums show their year, and tracks show their album. Not done: paging beyond the first 75 results, searching inside the truth table.

## File truth table
`i` replaces the two lists with every analysed track of your library in one table: marker (✗ problem, ! warn, · note), track, album, format (codec, bits/kHz), DR, LUFS, true peak and the finding labels, with the selected track's numbers and every finding explained underneath. `s` cycles the order (worst findings first, lowest DR, loudest, highest true peak, library order), `o` keeps only tracks with findings, `d` keeps only tracks that have copies and puts a recording's copies side by side (the "Copies" column shows `×2`, with `=` when one is bit-identical; the detail lists each copy's album, format and loudness; `d` again goes back; the sort `s` also has "copies together"), `j`/`k`, `PgUp`/`PgDn`, `g`/`G` move, `enter` plays from there and **the list shown becomes the queue**, so `n`/`p` walk through, say, all the clipped files; `i` or `esc` goes back. The first `i` loads the data in the background and the title shows `loading n/N` meanwhile; the table is kept until you quit. A server with `GET /api/v1/tracks?truth=1` (300 tracks a page) is read in a few requests; an older one without it is read album by album (`/albums/{id}`, four threads; 74 albums took 8 s). Only your own analysed tracks appear. Duplicates are found across the whole library by the server, so they show here too.

## Cover
The album cover is fetched in the background from `/cover/{album}` with the token (path and query only, so a proxy's scheme or host does not matter), decoded with the `image` crate (JPEG and PNG), scaled to 256 px at most and drawn with block characters (`src/blocks.rs`, below), a square as tall as the meters area, left of the meters in the player and in full screen, only when the area is at least 70 columns wide and the cover has loaded. Terminal image protocols (kitty, iTerm2, sixel) are not used, so that it works in every terminal; the picture is made of characters.

**Cover detail** (2026-11-10). Each cell shows two colours, and `blocks::render` chooses per cell which two and which part each takes. Default: quadrant blocks (`▘▝▖▗▚▞▌▐▀▄▛▜▙▟█`, 2 x 2 pixels a cell, twice the detail across of half blocks); `MAGNETITE_COVER=half` switches to half blocks (`▀`, 1 x 2) for a terminal or a font without the block-element characters. The cover is resized with Lanczos and sharpened a little (`unsharpen`) to the pixel grid of the area, once per size (the cells are kept until the area or the cover changes). Without true colour (macOS Terminal.app: no `COLORTERM`), the colours come from the 256-colour palette's cube and grey ramp (`blocks::nearest`, nearest by distance; the old rounding turned a dark red such as maroon into flat grey), and the error of each cell's colours is spread over the cells still to be drawn, Floyd-Steinberg style, so gradients do not step in a few flat bands. The spread is deliberately mild (60%, at most 28 levels a pixel; of the colour part of the error only 15% for a grey pixel up to 50% for a saturated one, and near-greys prefer the grey ramp), because full strength dotted flat colours with speckle: it keeps the brightness error and gives up part of the colour accuracy. Checked on real covers by drawing the cells back to pixels (`MAGNETITE_PREVIEW=cover.jpg MAGNETITE_PREVIEW_OUT=dir cargo test preview -- --ignored`). Not done: sextants/octants (more pixels a cell, newer Unicode that fewer fonts have), an image protocol where the terminal announces one.

## Resume
The track and position are saved in `tui.json` (`last`) when a track starts, every 5 s while playing and on quit. The next start opens that album with the track selected, shows its cover and says paused; `space` starts it from the saved position (`,` `.` move that position first, `enter` plays something else). Nothing plays by itself. The saved album is the one the queue came from (not the one open in the list). If the album or track is gone or no longer shared with you, it starts as before.

## No meters
With every meter removed the player shows the cover on the left (a square, up to a third of the width) and beside it the track (title, artist), the album (title, year, track n of N, album DR), the format (codec, effective bits / sample rate, "stored as" when padded), the file truth (DR and its class, LUFS, LRA, true and sample peak, clipped runs, content and cut-off frequency) and every finding with its explanation (problem in red, warn in accent2, note muted); the full screen is the cover big in the middle with the same information centred below it. Tracks that are not yours or not analysed say so. The empty list is saved in `tui.json`, so it stays that way after a restart (a client that never chose anything still starts from the account's list).

## Loudness matching
`L` cycles off, album and track (saved in `tui.json` as `loudness`, default off). The gain comes from the stored integrated LUFS of the track (owner's analysed tracks only; others play untouched): the target is -16 LUFS. **Track** brings every track to the target on its own; **album** gives every track of the album the one gain that brings the album's mean LUFS to the target (from the tracks of that album in the queue), so a quiet intro stays quieter than the single, which is usually what "albums should not jump" means. A boost never pushes the track's true peak above -1 dBTP, and a gain is limited to +12 / -24 dB. The gain is applied to the output only, eased over 15 ms; the meters keep showing the file's own level (that is the point of the file-truth numbers), so a level-matched track looks as loud on the meters as it was mastered. The indicator is in the Now playing title (`LM album -2.3 dB`, or `n/a` when the track has no measurement) and in the status line when you press `L`. Code: `src/loudness.rs` (the maths, tested), `Player::set_gain` in `src/audio.rs`.

## A/B compare
In the file-truth table, `a` compares the selected track with another copy of the same recording: same artist and title (case and spacing aside) and a length within 2 s, the server's rule for "another copy" (`ab::copies`; copies on other albums come first; the same rule marks the "Copies" column of the table, plus the server's exact-duplicate flag, which also catches identical audio under different tags). Two output streams play in lock step, both paused until each has buffered a second, then released together; one is heard, the other is muted but keeps decoding, so switching is instant and at the same place (checked on a real pair: both sides started after 1.7 s and were 0 ms apart after 4 s). The screen is the two sides next to each other, A and B, each with its title, album, format line (codec, bits/kHz, DR, LUFS, true peak), its gain and its own meters (the first two of your meters; a muted side still shows its file's level), then the difference B against A (loudness, DR, true peak, content ceiling), the progress and the keys. `1`/`2` or `x` choose what you hear, `g` switches "same loudness" (on by default: both come down to the quieter copy's LUFS, attenuation only, because the louder copy always sounds better), `[`/`]` pick another copy as B when there are several, `space` pauses both, `,`/`.` seek both, `m`/`M`/`+`/`-`/`t`/`c` work as usual, `esc` or `a` leaves and what you hear keeps playing in the normal player (B becomes the playing track if you were hearing B). Needs the analysed tracks (the truth table) and playable (yours) copies; the second stream is a second cpal output on the same device. Not done: choosing the two tracks by hand (only copies the rule finds), a blind mode that hides which is which, an ABX test, comparing across a length difference (both play from the same time, not aligned by content).

## Media keys and system controls
`src/media.rs` uses the `souvlaki` crate: the keyboard's play/pause, next and previous keys, seek, and the system's now-playing display (title, artist, album, length, position, paused or playing) on macOS (Control Center, Now Playing), Linux (MPRIS over D-Bus with the pure-Rust zbus backend, so no `libdbus` is needed: `playerctl`, GNOME and KDE widgets, waybar) and Windows (system transport controls). Commands run exactly like the keys (play on a restored track starts it where it stopped). Volume is ignored (the client has none). The cover is sent as a pixelated copy: the real one needs the token, which the system cannot present, so once the cover has loaded the client writes a 32 x 32 mosaic of it (the picture the terminal shows, scaled up to 512 x 512 with hard edges) to `~/.config/magnetite/artwork/` (one file, the older ones removed) and hands the system its `file://` url; the display gets the title first and the cover a moment later. macOS gives media keys to the main run loop, which a terminal program does not run, so the main loop gives it a turn every 33 ms (`media::pump`). If the platform refuses, the client runs without it.
Status: registering with the system works on macOS (checked 2026-11-10); a media key press, Control Center and the Linux and Windows builds are not tried yet. On macOS the keys go to whichever app last played, so another player may still catch them.

## Meter peek
The playing track in the track list carries a live 8-bar spectrum (eighth blocks, from the 24 spectrum bands, the loudest of each share), in the meters' accent colours (the cover's when the tint is on); on the selected row it takes the page colour so it stays visible on the accent background. Paused, it is a flat low line. It shows only while that album is the one open in the list.

## Cover colours
The meters take their two accent colours (accent and accent2) from the album cover, and ease to the next album's colours over about 0.3 s. `src/cover.rs` `palette()`: the cover is scaled to 32 x 32, every pixel is weighted by saturation x value (grey, black and white count for nothing), the weights go into 36 hue bins, the strongest hue is the accent and the strongest one at least 40 degrees away (with at least 12% of the colour) is accent2; with a single hue, accent2 is a lighter tone 30 degrees on. Both are lifted to a saturation of at least 0.55 and a brightness of 0.78 or more so they read on a dark theme. A cover with no colour keeps the theme's own colours, and the red zones stay red. `c` switches it off (saved in `tui.json` as `tint`, default on). Only the meters are tinted, not the lists, borders or progress bar. Not done: a light-theme variant is in `palette(img, light)` but nothing passes `light = true` yet.

## Themes
The six built-in themes are read from `resources/js/magnetite/themes.json` at build time (one source with the web player). Your own go in `~/.config/magnetite/themes/*.json` (a theme object or a list; same bundle as the web, only `colors` is used; a theme with a built-in's id replaces it). `magnetite theme` lists them, `magnetite theme ID` chooses, `t` cycles in the player; the choice is saved in `tui.json`. Mapping: `bg` page, `surface` panes, `text`, `muted` borders and secondary text, `accent` focus, selection, spectrum bottom and VU, `accent2` spectrum top, VU above -12 dB and the playhead (red above -3 dB). Radius, font and the visualizer look of a theme do not apply. Without `COLORTERM=truecolor` (Terminal.app) colours fall back to the nearest of the 256-colour palette, so use iTerm2, Ghostty, kitty or WezTerm for the exact look.

## Rules kept
- Only the API is used; tracks without `stream_url` (not shared with the viewer) are greyed out and skipped.
- The file-truth line (codec, bits/rate, DR, findings) and the LUFS / LRA / true peak readouts come from `TrackResource.truth` (owner's tracks only); the live meters are computed locally.

## Known limits (v0)
- Playback streams in 256 KB Range chunks with 3 chunks of read-ahead (`src/stream.rs`), so it starts after the first chunk and an MP4 with its index at the end costs one more chunk. The next track is opened in the background. Chunks stay in memory for the track's life. Needs `Range` support from `/stream` (it has it). On a slow link (2026-11-09 from home: about 20 KB/s to magnetite.stackcare.pt, for static files too, while other hosts gave 3 MB/s) playback starts after about 23 s and then stalls: a 19 MB ALAC needs far more.
- Seek is `,`/`.` (±10 s, coarse); no seek bar click. No queue view, no search, no playlists or shared tab yet.
- Decoding is symphonia 0.6.1 (FLAC, ALAC, MP3, AAC, Vorbis, WAV) plus Opus through `symphonia-adapter-opus-rs` (pure Rust, no `cmake` or `libopus`), registered in `codecs()` in `src/audio.rs`. Checked against ffmpeg on real tracks from the library (2026-11-09): Opus 75 dB SNR, Vorbis 139 dB, ALAC 133 dB, all the same length; the ignored test `matches_ffmpeg_on_a_real_file` does it for any file. Seeks are exact: the reader lands at or before the target and the frames before it are dropped (Opus: up to 6.5 ms late, its pre-skip). M4A has no gapless trimming in symphonia, so an ALAC file starts with about 48 ms of encoder-delay silence that ffmpeg would cut.
- Resampling is linear (fine for meters, not audiophile); output must be f32 (macOS default).
- Multichannel is reduced to the first two channels.
- The loudness meter is live (`ebur128`); the LUFS in the info line is the stored analysis of the whole file.
